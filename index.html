SKYFALL

Microarchitectural Data Sampling on AMD

A transient execution attack that reaches across confidential virtual machines, microcode, and system management memory.

IEEE S&P 2027

Paper ↗Code ↗Cite this paper ⧉

Summary

SKYFALL is a microarchitectural data sampling attack on AMD processors. It allows privileged software to recover sensitive data from inside the CPU, crossing isolation boundaries that are supposed to protect confidential virtual machines, microcode, and System Management Mode memory.

The attack builds on Transient Scheduler Attacks (TSA). We show that AMD’s cache way predictor computes an address hash for fast lookup not only virtual addresses, but also physical and CPU-internal addresses. An attacker can exploit colliding address hashes to sample data that is architecturally inaccessible.

We combine this finding with gaps in existing TSA mitigations to demonstrate three attacks: extracting SEV-SNP guest state, recovering decrypted microcode patches, and leaking protected SMM state. We reported our findings to AMD, which assigned CVE-2026-40671.

What went wrong?

What is a µtag?

A CPU cache keeps recently used data close to the processor. In AMD’s L1 data cache, a memory location can occupy one of several slots, called ways. To avoid checking every way on every access, the CPU predicts which way to read.

This prediction uses a micro-tag (µtag): a small hash derived from an address. AMD initally purposed the µtag to accelerate cache lookup while waiting for the TLB to return the physical address. A matching µtag is a hint to the CPU that the desired data is in a particular way; the full physical tag still has to be checked. Different addresses can produce the same µtag, a situation called a collision.

Software mostly accesses memory through virtual addresses, which the CPU translates into physical addresses. Way prediction can begin before this translation finishes. Prior to SKYFALL, TSA attacks exploited µtags derived from virtual addresses. Our analysis shows that privileged instructions and CPU-internal memory also have a µtag derived from the physical addresses.

Physical and virtual µtags can alias

A sensitive access through a physical address can leave data and its µtag in the L1 cache. An attacker then chooses a virtual address with a colliding µtag. Although that address maps to different memory, it can select the way containing the sensitive value.

TSA-L1 can transiently forward data from that predicted way before the CPU resolves the mismatch. The attacker amplifies a bit of the forwarded value into scheduler contention and measures it with Performance Monitoring Counters (PMCs). Repeated measurements recover the data without architectural access.

Some sensitive paths return without cleanup

AMD’s VERW-based TSA mitigation clears the relevant predictor state. However, some privileged execution paths introduce sensitive data and return without performing this cleanup. Those paths include an aborting VMRUN, the microcode patch loader, and the SMM exit path examined in our experiments.

For example, VMRUN loads and decrypts confidential guest state before completing all checks. If a later check fails, the instruction aborts. The guest is never entered, but its plaintext state is already in the cache and remains reachable through TSA-L1.

We use AMD’s Instruction Based Sampling (IBS) to trace these internal instruction paths and understand where the protections are missing. The root cause is the combination of physical/virtual µtag aliasing and incomplete predictor-state cleanup.

What did we exploit?

SEV-SNP confidential virtual machines

AMD SEV-SNP is designed to protect a virtual machine from a malicious host, including by encrypting its memory and saved register state. We show that a malicious hypervisor can use an aborting VMRUN to bring decrypted guest state into the L1 cache and then extract it with TSA-L1.

We recover register state from the Virtual Machine Save Area (VMSA) and demonstrate AES-XTS disk-encryption key recovery. The key demonstration uses a modified guest kernel to trigger a VM exit when the key is in registers. We also recover guest memory at three fixed cache-line offsets within a selected page: 0x0c0, 0x380, and 0x3c0. This memory primitive does not expose every byte in a page.

Decrypted microcode patches

The microcode patch loader decrypts updates in a CPU-internal, HyperTransport-addressed region. We sample the residual state and recover decrypted microcode patch contents on all three tested systems.

On the tested EPYC 7313, we additionally recover the CMAC key used before the EntrySign mitigations. The tested EPYC 9124 and 9334 systems already include those mitigations and do not expose that key through the same procedure, but still leak decrypted patch contents.

System Management Mode memory

System Management Mode (SMM) runs privileged firmware in memory that is normally inaccessible even to the operating-system kernel. After returning from SMM, we use TSA-L1 to recover fields from its protected State Save Area, including SMBASE, CR3, and R13.

All tested field values are recovered with 100% accuracy in the experiments. This demonstrates leakage from protected SMM memory; it is not a demonstration of a complete arbitrary SMM memory dump.

Frequently asked questions

What privileges does an attacker need?+

The confidential-VM attack requires a malicious host or hypervisor. The microcode and SMM demonstrations also use privileged local software. The attacker needs access to the relevant instruction paths and performance counters. These privileges are especially relevant to confidential computing, where the host is explicitly outside the guest’s trust boundary.

Does the attack require physical access?+

No physical manipulation is needed for our demonstrations. The attacks run in software with the privileges described above.

Does SKYFALL break memory encryption?+

It does not break the underlying encryption algorithm. Instead, it samples plaintext after the CPU has decrypted it internally. Encrypting memory does not prevent leakage through residual microarchitectural state.

How reliable and fast is the attack?+

In controlled bulk TSA-L1 experiments, we measure 463 KiB/s on EPYC 7313 and 443 KiB/s on EPYC 9124 at approximately 98.7% mean bit accuracy with one sample per bit. These are primitive-level measurements, not end-to-end secret-extraction rates. The attacks require calibration and repeated measurements; noise and the targeted instruction path affect reliability. The microcode-loader path produces a weaker and less stable signal.

Why do the existing TSA mitigations miss it?+

VERW-based predictor clearing works when it executes, but sensitive physical-address and CPU-internal paths are not all covered. A failing VMRUN returns without the cleanup normally applied at confidential guest exit.

Is there a patch or CVE?+

AMD assigned CVE-2026-40671. AMD will likely provide microcode updates to patch the vulnerability.
